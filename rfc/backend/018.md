| 항목 | 값 |
|------|-----|
| 상태 | Draft |

## 1. 아키텍처 요약

### 1.1 목표

SOTA+++ Agent Runtime은 "LLM 호출"이 아니라 **Session Actor + Event Sourcing + Deterministic Replay + Trajectory CI**를 SSOT로 잠그는 것이다.

[RFC-015](015.md)가 6 Layer + 12 Gate로 엔진급 SOTA+++를 정의했다면, 본 RFC는 그 위에 **서버급 운영 계층**(Queue, EventStore, ArtifactStore, EnginePort)을 고정하고, 모든 구성요소의 계약과 스키마를 최종 확정한다.

### 1.2 최종 형태

| 구성요소 | 역할 |
|----------|------|
| **UI (VSCode/Web/Desktop)** | thin client, event stream 구독 + 승인/취소만 수행 |
| **API (SessionManager)** | session 생성/메시지 라우팅, auth, stream fanout |
| **Session Actor (Worker)** | 단일 writer 상태머신, 모든 변경은 이벤트로만 기록 |
| **Model Runtime** | routing + schema enforcement + fallback |
| **Tool Sandbox** | side-effect 통제, dry-run/preview-first |
| **Artifact Bus** | 모든 산출물 content-addressed 저장 |
| **Eval/Replay** | golden trajectory 회귀, semantic equivalence 게이트 |

### 1.3 RFC-015와의 관계

| RFC-015 범위 | RFC-018 확장 |
|-------------|-------------|
| 6 Layer 개념 | 7 구성요소로 재구성 (API/Queue/Worker 분리) |
| Session Kernel 개념 | Session Actor + EventStore + optimistic concurrency 구체화 |
| Artifact Bus 개념 | content-addressed 저장 + artifact 메타 테이블 확정 |
| Deterministic Replay 개념 | 3 replay 모드 + gate 묶음 확정 |
| 12 Gate | 13 Gate로 확장 (gate-event-log-replayable 추가) |
| Tool Sandbox 개념 | ToolMetadata SSOT + 실행 규칙 확정 |
| Recovery Engine 개념 | 표준 복구 루프 + 표준 에러 타입 확정 |
| - | EnginePort 포트 계약 신규 |
| - | Queue/Worker 모델 SSOT 신규 |
| - | Semantic Patch Equivalence v1 신규 |

## 2. 런타임 구성요소 고정 SSOT

### 2.1 컴포넌트

| 컴포넌트 | 역할 |
|----------|------|
| **SessionManager (API)** | `SendMessage(session_id, msg)` 라우팅, SSE/WebSocket stream 제공 |
| **Queue** | session 단위로 actor mailbox 보장 (키 기반 파티셔닝) |
| **ActorWorker** | `session_id` -> 단일 actor 인스턴스 (또는 shard 내 단일 소비자) |
| **EventStore (Postgres)** | append-only, optimistic concurrency |
| **ArtifactStore (S3/Blob)** | `sha256:` 주소 기반 저장 |
| **EnginePort (Reasoning Engine)** | 외부/내부 구현체 교체 가능, 출력은 IR + EvidenceRef만 허용 |

### 2.2 단일 writer 규칙

| 규칙 | 설명 |
|------|------|
| update 금지 | "현재 상태"를 DB에 직접 update 금지 |
| append-only | 반드시 `append_event()`만 가능 |
| reduce 복원 | 상태는 `reduce(events[])` 로만 재구성 |

이 규칙은 [RFC-015](015.md) 8.1절 Single Writer Rule의 서버급 확장이다.

## 3. Session Actor 상태머신 v1

### 3.1 상태

[RFC-015](015.md) 3.1절 + [RFC-017](../017.md) 2.5절을 기준으로 확정한다.

| 상태 | 설명 |
|------|------|
| `IDLE` | 대기 |
| `ANALYZING` | 컨텍스트 수집/분석 |
| `PLANNING` | 계획 수립 |
| `AWAITING_APPROVAL` | 사용자 승인 대기 |
| `EXECUTING` | 패치/명령 적용 |
| `VALIDATING` | 검증 |
| `RECOVERING` | 에러 복구 중 |
| `FAILED` | 실패 (복구 불가) |
| `COMPLETED` | 완료 |

### 3.2 전이 규칙 (핵심)

| 전이 | 조건 |
|------|------|
| `PLANNING` -> `AWAITING_APPROVAL` | `risk=MEDIUM\|HIGH` 또는 `sideEffect=WRITE\|EXEC` 포함 시 |
| `EXECUTING` -> `RECOVERING` | tool/model/engine error normalized 발생 시 |
| `RECOVERING` -> `PLANNING` | recovery plan 생성 성공 시 |
| `VALIDATING` -> `FAILED` | validation gate 실패 + recovery 불가 시 |

### 3.3 전체 전이 다이어그램

```
IDLE
  -> ANALYZING         (USER_PROMPT_RECEIVED)
    -> PLANNING         (CONTEXT_SNAPSHOT_CREATED)
      -> AWAITING_APPROVAL  (risk >= MEDIUM or sideEffect in [WRITE, EXEC])
        -> EXECUTING        (APPROVAL_GRANTED)
      -> EXECUTING          (risk == LOW and sideEffect == READ)
        -> VALIDATING       (TOOL_CALL_FINISHED, PATCH_APPLIED)
          -> COMPLETED      (VALIDATION_PASSED)
          -> RECOVERING     (VALIDATION_FAILED, recoverable)
          -> FAILED          (VALIDATION_FAILED, not recoverable)
        -> RECOVERING       (ERROR_NORMALIZED)
          -> PLANNING       (RECOVERY_PLAN_ACCEPTED)
          -> FAILED          (recovery exhausted)
```

## 4. Event Sourcing 스키마 v1

### 4.1 EventStore 테이블 (Postgres)

```sql
CREATE TABLE agent_session (
  session_id   TEXT PRIMARY KEY,
  created_at   TIMESTAMPTZ NOT NULL,
  last_event_seq BIGINT NOT NULL DEFAULT 0,
  status       TEXT NOT NULL
);

CREATE TABLE agent_event (
  session_id     TEXT NOT NULL,
  seq            BIGINT NOT NULL,
  ts             TIMESTAMPTZ NOT NULL,
  type           TEXT NOT NULL,
  payload_json   JSONB NOT NULL,
  actor_version  TEXT NOT NULL,
  prev_event_hash TEXT NOT NULL,
  event_hash     TEXT NOT NULL,
  PRIMARY KEY (session_id, seq)
);

CREATE INDEX agent_event_ts_idx ON agent_event (ts);
```

### 4.2 원칙

| 원칙 | 설명 |
|------|------|
| **단조 증가** | `seq`는 session 단위 단조 증가 |
| **CAS** | append 시 `agent_session.last_event_seq`와 CAS(optimistic)로 충돌 방지 |
| **tamper-evidence** | `prev_event_hash` -> `event_hash` 체인으로 변조 감지 확보 (필요 시) |
| **payload ref** | 이벤트 payload에 큰 본문 금지, artifact ref만 저장 ([5절](#5-artifact-bus-v1) 참조) |

### 4.3 이벤트 타입 SSOT

| 이벤트 타입 | 상태 전이 트리거 |
|------------|----------------|
| `USER_PROMPT_RECEIVED` | IDLE -> ANALYZING |
| `CONTEXT_SNAPSHOT_CREATED` | ANALYZING -> PLANNING |
| `PLAN_IR_ACCEPTED` | PLANNING 내부 |
| `APPROVAL_REQUESTED` | PLANNING -> AWAITING_APPROVAL |
| `APPROVAL_GRANTED` | AWAITING_APPROVAL -> EXECUTING |
| `TOOL_CALL_STARTED` | EXECUTING 내부 |
| `TOOL_CALL_FINISHED` | EXECUTING 내부 |
| `PATCH_PREVIEW_CREATED` | EXECUTING 내부 |
| `PATCH_APPLIED` | EXECUTING -> VALIDATING |
| `VALIDATION_STARTED` | VALIDATING 내부 |
| `VALIDATION_PASSED` | VALIDATING -> COMPLETED |
| `ERROR_NORMALIZED` | any -> RECOVERING |
| `RECOVERY_PLAN_ACCEPTED` | RECOVERING -> PLANNING |

### 4.4 이벤트 payload 규약

```typescript
type AgentEventPayload = {
  event_type: string;
  session_id: string;
  seq: number;
  ts: string;           // ISO 8601
  actor_version: string;
  artifact_refs?: string[];  // sha256:... (큰 데이터는 ref만)
  metadata?: Record<string, unknown>;
};
```

## 5. Artifact Bus v1

### 5.1 저장 규약

| 규칙 | 설명 |
|------|------|
| **content-addressed** | 모든 산출물은 `sha256:<hex>` 주소 |
| **payload 분리** | 이벤트 payload에는 큰 본문 금지, artifact ref만 저장 |
| **불변** | 한번 저장된 artifact는 수정 불가 (append-only) |

[RFC-016](../016.md) 4절의 blob meta/payload 분리 구조와 호환한다:

```
artifact/<sha256_hex>/
  meta.json
  payload.bin (또는 payload.txt, payload.json)
```

### 5.2 Artifact 메타 테이블 (옵션: Postgres)

```sql
CREATE TABLE agent_artifact (
  artifact_id  TEXT PRIMARY KEY,       -- sha256:...
  media_type   TEXT NOT NULL,          -- application/json, text/plain, application/diff
  byte_size    BIGINT NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL,
  storage_uri  TEXT NOT NULL           -- s3://... or local path
);
```

### 5.3 대표 artifact 목록

| artifact | media_type | 용도 |
|----------|-----------|------|
| `raw_model_output.json` | application/json | 모델 원본 출력 |
| `plan_ir.v2.json` | application/json | PlanIR v2 ([RFC-013](../013.md)) |
| `patch_ir.v2.json` | application/json | PatchIR v2 (reversible) |
| `revert_patch_ir.v2.json` | application/json | Revert PatchIR |
| `tool_result.json` | application/json | Tool 실행 결과 |
| `validation_log.txt` | text/plain | 검증 로그 |
| `workspace_snapshot.tar.zst` | application/zstd | 워크스페이스 스냅샷 (또는 ref set) |

## 6. Queue/Worker 모델 SSOT

### 6.1 세션 라우팅 (필수)

| 규칙 | 설명 |
|------|------|
| **queue key** | `session_id` |
| **ordering** | 같은 session 메시지는 항상 같은 shard/consumer로 전달 |
| **scale-out** | worker scale-out 시에도 per-session ordering 보장 |

### 6.2 구현 옵션

| 옵션 | 특징 |
|------|------|
| **Redis Streams** | consumer group, key partitioning 직접 설계 |
| **Kafka** | partition key=session_id 정석 |
| **SQS FIFO** | message group id=session_id |

선택은 운영 환경에 따르며, 위 3개 모두 6.1의 세션 라우팅 규칙을 만족한다.

### 6.3 워커 무상태 원칙

| 원칙 | 설명 |
|------|------|
| **상태 재구성** | 워커는 이벤트를 읽고, `reduce`로 상태 재구성 후, 새 이벤트 append |
| **in-memory cache** | in-memory state cache는 허용하되, crash 시 이벤트 replay로 복구 가능해야 함 |
| **무상태** | 워커 인스턴스는 교체/재시작해도 정합성 유지 |

## 7. Reasoning Engine 포트 계약 (EnginePort)

### 7.1 EnginePort 입력/출력 고정

**입력**

| 필드 | 설명 |
|------|------|
| `SessionContextRef` | workspace snapshot refs, recent events refs |
| `Goal` | 사용자 목표 |
| `Constraints` | approval policy, tool allowlist, budget |
| `Hints` | optional, 추가 컨텍스트 |

**출력 (허용 형태)**

| 출력 타입 | 설명 |
|----------|------|
| `PlanIR_v2` | 계획 IR ([RFC-013](../013.md)) |
| `PatchIR_v2` | 패치 IR ([RFC-013](../013.md)) |
| `RunIR_v2` | 실행 IR ([RFC-013](../013.md)) |
| `EvidenceRef[]` | 근거 artifact ref 목록 |
| `NormalizedError` | 표준 에러 ([10절](#10-recovery-engine-v2) 참조) |

### 7.2 엔진 금지 행위

| 금지 | 이유 |
|------|------|
| tool을 직접 실행 | 실행은 Runtime(Tool Sandbox)이 담당 |
| 파일을 직접 수정 | 수정은 Runtime이 PatchIR를 통해 수행 |
| 상태를 직접 update | 상태 변경은 이벤트 append만 허용 (2.2절) |

**엔진은 "결정/추론"만 하고, 실행은 Runtime이 담당한다.**

### 7.3 EnginePort 계약 스키마 위치

```
schemas/agent-ux/contracts/engine-port.v1.json
```

## 8. Model Runtime v2 (Routing + Contract Enforcement)

[RFC-012](012.md)의 Model Runtime을 v2로 확장한다.

### 8.1 라우팅 SSOT

| 항목 | 설명 |
|------|------|
| **task_kind 기반** | `PLAN` / `PATCH` / `RECOVERY` / `CHAT` 별 preferred + fallback |
| **schema enforcement** | JSON schema + semantic validation |
| **violation loop** | 최대 N회 (권장 2회) 재질의, 이후 hard fail 또는 recovery로 전환 |

라우팅 정책 SSOT: `schemas/agent-ux/policy/model-routing.v1.yaml` ([RFC-012](012.md) 2절 확장)

task_kind에 `RECOVERY`를 추가한다:

```yaml
task_kinds:
  PLAN:
    preferred: [...]
    fallback: [...]
    constraints:
      enforce_schema: PlanIR_v2

  PATCH:
    preferred: [...]
    fallback: [...]
    constraints:
      enforce_schema: PatchIR_v2

  RECOVERY:
    preferred: [...]
    fallback: [...]
    constraints:
      enforce_schema: PlanIR_v2
      max_retries: 2

  CHAT:
    preferred: [...]
    fallback: []
```

### 8.2 Provider 에러 표준화

[RFC-012](012.md) 3절 에러 타입을 SSOT로 재확인한다:

| 에러 코드 | 설명 |
|----------|------|
| `MODEL_TIMEOUT` | 호출 타임아웃 |
| `MODEL_RATE_LIMIT` | Rate limit 초과 |
| `MODEL_SCHEMA_VIOLATION` | IR schema 검증 실패 |
| `MODEL_PROVIDER_ERROR` | Provider 내부 에러 |

## 9. Tool Sandbox v2 (Side-effect 통제)

[RFC-015](015.md) 6절을 v2로 확장한다.

### 9.1 ToolMetadata SSOT (필수 필드)

```typescript
type ToolMetadata = {
  id: string;
  sideEffect: "READ" | "WRITE" | "EXEC";
  idempotent: boolean;
  reversible: boolean;
  dryRunSupported: boolean;
  approvalRequired: boolean;
  riskLevel: "LOW" | "MEDIUM" | "HIGH";
};
```

SSOT 위치: `schemas/agent-ux/policy/tool-metadata.v1.yaml` ([RFC-015](015.md) 16절)

### 9.2 실행 규칙

| 규칙 | 설명 |
|------|------|
| **preview 필수** | `WRITE` / `EXEC`는 반드시 preview artifact 생성 |
| **approval 필수** | approval 없이는 `WRITE` / `EXEC` 실행 불가 (정책 기반) |
| **artifact 저장** | 모든 tool 결과는 artifact로 저장 후 이벤트에 ref만 기록 |
| **cancellation** | cancellation token 필수 |

### 9.3 Tool 결과 흐름

```
Tool 실행
  -> 결과 생성
  -> ArtifactStore에 저장 (sha256: 주소)
  -> TOOL_CALL_FINISHED 이벤트 append (artifact_ref만 포함)
  -> Actor 상태 reduce로 반영
```

## 10. Recovery Engine v2

[RFC-007](../007.md) Recovery + [RFC-015](015.md) 9절을 확장한다.

### 10.1 표준 복구 루프

```
1. ERROR_NORMALIZED 이벤트 append
2. recovery prompt/inputs 구성 (근거 evidence ref 포함)
3. RECOVERY_PLAN 생성 (EnginePort 호출)
4. 승인 필요 시 AWAITING_APPROVAL로 이동
5. 성공 시 기존 플랜과 merge 또는 supersede
```

### 10.2 표준 에러 타입 (엔진/툴/모델 공통)

| 에러 타입 | 계층 | 설명 |
|----------|------|------|
| `ENGINE_INSUFFICIENT_CONTEXT` | engine | 추론에 필요한 컨텍스트 부족 |
| `ENGINE_CONTRADICTION` | engine | 입력 간 모순 감지 |
| `TOOL_NONDETERMINISTIC_FAILURE` | tool | 비결정적 도구 실패 |
| `TOOL_PERMISSION_DENIED` | tool | 권한 부족 |
| `MODEL_TIMEOUT` | model | 모델 호출 타임아웃 |
| `MODEL_RATE_LIMIT` | model | Rate limit 초과 |
| `MODEL_SCHEMA_VIOLATION` | model | IR schema 검증 실패 |
| `MODEL_PROVIDER_ERROR` | model | Provider 내부 에러 |
| `VALIDATION_FAILED` | validation | 검증 실패 |
| `TIMEOUT` | any | 일반 타임아웃 |

기존 [RFC-007](../007.md) `AgentErrorV1`의 `error_code`와 매핑한다:
- `layer` 필드 = 위 테이블의 "계층"
- `error_code` 필드 = 위 테이블의 "에러 타입"
- `retryable` 필드 = 에러 타입별 기본값 + 정책 override 가능

### 10.3 Recovery 횟수 제한

| 정책 | 기본값 |
|------|--------|
| max_recovery_attempts | 3 |
| max_recovery_depth | 2 (recovery 중 recovery) |
| recovery_timeout_ms | 60000 |

초과 시 `FAILED` 상태로 전환한다.

## 11. Deterministic Replay + Trajectory CI v2

[RFC-014](014.md) + [RFC-015](015.md) 4절 + 10절을 통합 확장한다.

### 11.1 Replay 모드

| 모드 | 모델 | 도구 | 용도 |
|------|------|------|------|
| `MODEL_MOCK + TOOL_MOCK` | mock | mock | CI 기본 (빠름, 결정적) |
| `MODEL_REAL + TOOL_MOCK` | real | mock | 모델 변화 감지용 |
| `MODEL_REAL + TOOL_REAL` | real | real | nightly 또는 수동 |

[RFC-015](015.md) 4.1절의 3 모드를 명칭 표준화한다.

### 11.2 Gate 묶음 (최종)

기존 SOTA+++ 12 Gate ([RFC-015](015.md) 13절) + 1 Gate 추가 = **13 Gate**:

| Gate | 출처 | 설명 |
|------|------|------|
| **gate-event-log-replayable** | 본 RFC | event log replay로 상태 복원 가능 |
| gate-ir-schema-zero-violation | [RFC-012](012.md) | IR schema 검증 실패 0건 |
| gate-ir-semantic-guard | 본 RFC | semantic validation 통과 |
| gate-tool-idempotency | [RFC-014](014.md) | Tool idempotency 검증 |
| gate-tool-dryrun-parity | [RFC-015](015.md) | dryRun 결과와 실제 실행 결과 일치 |
| gate-approval-policy-enforcement | [RFC-014](014.md) | 승인 정책 준수 |
| gate-artifact-hash-stability | [RFC-015](015.md) | artifact hash 재현성 |
| gate-agent-trajectory-golden | [RFC-014](014.md) | Golden trajectory 회귀 |
| gate-recovery-trajectory | [RFC-014](014.md) | Recovery 시나리오 수렴 |
| gate-ast-equivalence | [RFC-015](015.md) | Patch semantic equivalence |
| gate-patch-revert-valid | [RFC-013](../013.md) | 모든 patch에 revert_diff 존재 |
| gate-ir-replay-determinism | [RFC-013](../013.md) | IR 재실행 시 결과 일치 |
| gate-step-partial-execution | [RFC-013](../013.md) | Step 단위 부분 실행 검증 |

### 11.3 Gate 이름 변경 정리

[RFC-015](015.md) `gate-model-schema-zero-violation`을 `gate-ir-schema-zero-violation`으로 명칭 변경한다 (IR이 검증 대상이므로). `gate-provider-error-normalization`은 [RFC-012](012.md)의 Tier 2 gate로 유지하며, SOTA+++ 13 gate에는 포함하지 않는다 (운영 gate로 분류).

## 12. Semantic Patch Equivalence v1

### 12.1 목적

모델 출력 변동으로 인해 diff 텍스트가 달라도 **"의미 동일"이면 PASS** 처리한다. 이는 `gate-ast-equivalence` ([RFC-015](015.md))의 구현 스펙이다.

### 12.2 프로파일 SSOT

```
schemas/agent-ux/eval/patch-equivalence.v1.yaml
```

| 필드 | 설명 |
|------|------|
| `language` | 대상 언어 |
| `parser` | AST 파서 |
| `normalize_rules` | 정규화 규칙 (import 정렬, 포맷팅 등) |
| `equivalence_rules` | 동치 판정 규칙 |
| `equivalence_profile` | trajectory 케이스별 프로파일 필수 지정 |

### 12.3 최소 지원

| 언어 | 규칙 |
|------|------|
| **TS/JS** | AST 기반 import reorder/formatting 무시 |
| **Python** | formatting/quote 스타일 무시 (가능하면 AST) |
| **Rust** | rustfmt 영향 무시 + use 정렬 허용 |

### 12.4 확장 포인트

언어별 파서는 플러그인으로 확장 가능하다 ([RFC-008](../008.md)). 플러그인이 `equivalence_profile`을 등록하면 해당 언어에 대한 semantic equivalence 검증이 자동으로 활성화된다.
