## 1. 목표

"대용량 채팅/타임라인 + 스트리밍 + 게이트" 기반 위에, **일반적인 Agent UX 유스케이스를 빠짐없이 커버하는 운영 모델** 정리.

### 1.2 커버 유스케이스

| # | 유스케이스 |
|---|------------|
| 1 | 외부 LLM 호출 결과 처리 (streaming 포함) |

| 3 | 파일 첨부 (업로드/드래그드랍/컨텍스트 주입) |
| 4 | 플러그인 내 기본 도구 (workspace/terminal/git/search 등) |
| 5 | 외부 플러그인 도구 (Jira/Notion/GitHub/Slack 등) |
| 6 | 세션/프로젝트 단위 상태, 스냅샷/복구, 타임라인/아티팩트 |

## 4. LLM 호출 (ModelPort 아키텍처, SOTA++)

### 4.1 원칙

LLM 관리는 **"모델 호출 도구"가 아니라 Agent Runtime이 소비하는 ModelPort**로 설계함 ([RFC-000](000.md)).

- Orchestrator는 모델을 직접 모름. **ModelPort**만 호출하고 결과를 AgentEvent로 환원
- 모델은 ToolCall intent(IR)만 생성. 도구 실행은 Tool Layer가 수행
- UI는 "스트리밍 델타"만 받음

### 4.2 흐름

1. UI 입력 → Orchestrator 이벤트 생성
2. Orchestrator가 **ModelPort.generate** 또는 **ModelPort.generateStream** 호출 (tool 아님)
3. Provider Adapter(Claude/OpenAI/local)가 외부 LLM 호출 수행
4. 응답 수신:
   - **streaming**: assistant_message_delta, tool_call_delta 등 구조화 이벤트 → APPEND_TEXT 등 델타로 변환
   - **non-streaming**: 최종 UPSERT_MESSAGE + SET_MESSAGE_STATUS(final) 델타
5. UI는 inputBuffer에 쌓고 16ms commit으로 반영

### 4.3 Model Protocol (model-protocol.v1.json)

- **ModelRequest**: model_id, session_id, turn_id, input.messages, tooling_spec, budgets
- **ModelResponse**: assistant_message, tool_calls[] (ToolCall intent만), meta
- **ModelStreamDelta**: assistant_message_delta, tool_call_delta, plan_ir_partial, patch_ir_partial

### 4.4 UI 델타 타입 권장

- UPSERT_MESSAGE (assistant message seed)
- APPEND_TEXT (stream chunk)
- SET_MESSAGE_STATUS (streaming/final/error)
- PUSH_TIMELINE (LLM 호출 시작/종료/사용량)
- UPSERT_ARTIFACT_REF (LLM이 생성한 큰 결과물은 blob ref로)

## 5. 외부 API 연결

### 5.1 원칙

외부 API는 전부 Tool Plugin으로만 연결. UI는 결과를 "요약 delta + 필요 시 blob ref"로 받음.

### 5.2 흐름

1. Plan 단계에서 API 호출 필요 시 Orchestrator가 `tool.http.request` 또는 플러그인 tool 호출
2. Tool에서 네트워크 호출 수행
3. 결과가 작으면 delta로 요약 전달, 크면 blob 저장 후 ref만 전달
4. UI "상세 보기" 시 ref를 통해 pull

### 5.3 Tool 카테고리 제안

| 카테고리 | 용도 |
|----------|------|
| http.request | 범용 |
| plugin.\<vendor\>.\<action\> | jira.searchIssues, notion.query 등 |
| internal.\<service\>.\<action\> | 사내 API |

SSOT: [RFC-006 5절](006.md).

### 5.4 결과 표현 표준

- **UI 표면**: "요약 카드 + 원본 보기"
- **타임라인**: request/response metadata 이벤트
- **아티팩트**: response body는 blob ref로 인덱싱

### 6.1 원칙

### 11.2 Architecture Decisions & Rationale

#### D1. Module-level cached dynamic import (5A, 5B)

```
loadMermaid() → mermaidPromise ?? import("mermaid").then(...)
loadXterm()  → xtermPromise  ?? Promise.all([import("@xterm/xterm"), ...])
```

**선택 이유**: mermaid(2MB), xterm(400KB)은 모든 세션에서 사용되지 않음. `React.lazy`는 component-level이라 hook 내 library 참조에 부적합. Module-level singleton promise가 가장 단순하면서 중복 로드를 원천 차단.

**Trade-off**: module state가 HMR 시 reset되지 않음 → dev에서 재초기화 필요 시 `vi.resetModules()` 필수. Production에서는 문제 없음.

**대안 분석**:
- `React.lazy` + `Suspense`: hook이 아닌 component만 가능. mermaid는 rendering library라 hook 패턴이 자연스러움
- Top-level `import mermaid`: main bundle 2MB 증가 — 불가
- Service Worker cache: 복잡도 대비 이점 없음 (HTTP cache로 충분)

#### D2. Delta 최소 확장 vs 파생 전용 (5C vs 5D)

| Feature | 접근 | Delta 추가 |
|---------|------|-----------|
| 5C Plan Checklist | 새 Delta 2종 (UPSERT_PLAN_CHECKLIST, UPDATE_PLAN_ITEM) | O |
| 5D Workspace Awareness | 기존 atom에서 파생 (cross-turn aggregation) | X |

**선택 이유**: Plan checklist은 에이전트가 **명시적으로 plan을 생성하는 새로운 시맨틱**이라 Delta로 표현하는 것이 프로토콜 계약상 정확함. Workspace awareness는 이미 존재하는 fileChange + toolCall 데이터에서 **view-level aggregation**만 하면 되므로 새 Delta 없이 derived atom으로 충분.

**원칙**: Delta는 시맨틱 경계(semantic boundary)에서만 추가. UI convenience를 위한 aggregation은 파생으로 해결.

#### D3. xterm.js 전면 교체 vs ANSI strip 유지 (5B)

기존 TerminalOutputViewer는 ANSI escape code를 strip한 뒤 `<pre>` 텍스트로 렌더링. Sprint 5에서 xterm.js 기반으로 전면 교체.

**선택 이유**: Code agent의 핵심 UX 중 하나가 터미널 출력. `npm test`, `git diff`, `cargo build` 등의 출력에서 색상은 **정보 밀도의 핵심 채널**. ANSI stripping은 정보 손실.

**Trade-off**: xterm.js는 canvas 기반이라 DOM text query 불가 → 기존 테스트 전면 재작성 필요. Mock 기반 hook 검증으로 전환하여 해결.

#### D4. Workspace Awareness: 새 패널 위치 (5D)

ChatPage subfooter에 ActivityFeed **위**에 배치, HeaderBar에 토글 버튼 추가.

**선택 이유**: Workspace awareness는 세션-전체 상태(cross-turn)이므로 개별 메시지 흐름(main area)이 아닌 persistent panel이 적합. ActivityFeed와 같은 subfooter slot이지만, workspace가 "맥락 정보"로서 activity보다 상위 우선순위.

### 11.3 What Went Well

1. **FSD 아키텍처의 확장성 검증**: 4개 기능이 entities/features/widgets/shared 경계를 자연스럽게 따름. Cross-cutting 의존성 없이 병렬 구현 가능했음.

2. **atomFamily 패턴의 일관성**: `planChecklistAtomFamily(turnId)`, `fileChangeSummaryByTurnAtom(turnId)` 등 기존 패턴을 그대로 확장. 새 기능 추가 시 boilerplate이 예측 가능하고 최소화됨.

3. **Delta Protocol의 exhaustive switch**: `useDeltaDispatcher.ts`의 `never` 타입 체크 덕분에 새 Delta 2종 추가 시 컴파일 타임에 미구현 감지. Runtime 누락 불가.

4. **Lazy chunk isolation**: `manualChunks` 설정 하나로 mermaid/xterm이 별도 청크로 분리. Main bundle 크기 변화 0.

5. **테스트 인프라 재사용**: `renderWithAtoms`, `createTestStore`, factory 패턴이 Sprint 1에서 구축한 대로 Sprint 5에서도 그대로 작동. 테스트 작성 속도가 구현 속도에 수렴.

---

### 11.4 What Could Be Improved

1. **Derived atom의 `store.set()` 불가 문제**: `workspaceFileGroupsAtom`, `planChecklistProgressAtomFamily`가 read-only derived atom이라 `renderWithAtoms({ initialValues })` 패턴에서 직접 설정 불가. Jotai의 `store.set()`이 write atom만 지원하기 때문. Widget 테스트에서 underlying writable atom을 통해 간접 설정해야 하므로 테스트 setup이 장황해짐.

   **개선안**: `createTestStoreWithDerived()` 유틸리티를 만들어 derived atom에 대해서도 override를 주입할 수 있게 하거나, widget 테스트에 `seedWorkspace(store, files[])` 같은 domain-specific helper 추가.

2. **Module-level state와 테스트 격리**: `useMermaidRenderer`, `useXtermTerminal`의 module-level promise cache가 테스트 간 공유됨. `vi.resetModules()`로 해결 가능하지만, 현재는 mock이 첫 import 시점에 고정되어 `await import()`로 우회. 더 깔끔한 방법: factory 함수로 loader를 주입 가능하게 만들기.

3. **Promise chain tick 문제**: `await act(() => Promise.resolve())`로 단일 microtask만 flush하면 multi-step promise chain (import → .then → .then)의 최종 상태를 잡지 못함. `waitFor()`로 전환했지만, 이는 polling 기반이라 테스트 의도가 불명확해짐.

   **근본 원인**: React Testing Library의 `act()`가 microtask queue를 완전히 drain하지 않는 설계 선택.
   **개선안**: 테스트 전용 `flushMicrotasks()` 유틸리티 또는 hook에 `onReady` callback 패턴 도입.

4. **xterm.js의 DOM testability**: canvas 기반 렌더링이라 출력 내용의 text assertion이 불가. Hook mock으로 우회했으나, 실제 렌더링 결과에 대한 visual regression test가 없음. Playwright/Chromatic 같은 VRT 도입 시점에서 커버.

### 11.6 Bundle Impact Analysis

```
                     Raw        Gzip       Loading Strategy
index.js           276 kB      86 kB      sync (initial)
markdown.js        343 kB     104 kB      sync (initial)
mermaid.core.js    498 kB     140 kB      lazy (on first ```mermaid block)
xterm.js           333 kB      84 kB      lazy (on first terminal output)
xterm addon-fit      2 kB       1 kB      lazy (co-loaded with xterm)
css                 73 kB      15 kB      sync (initial)
```

**Critical path**: `index.js` + `markdown.js` + `css` = **205 kB gzip**. Sprint 4 대비 변화 없음.

mermaid + xterm은 사용자가 해당 기능을 처음 트리거할 때만 로드. 평균 세션에서 mermaid를 사용하는 비율은 낮으므로 대부분의 사용자는 84 kB(xterm)만 추가 로드.

**Recommendation**: mermaid chunk가 140 kB gzip으로 가장 크므로, 자주 사용되지 않는 diagram type(architecture, sankey, requirement 등)을 제외하면 ~80 kB gzip으로 감소 가능. 추후 사용 통계 기반 결정.

### 11.7 Pattern Catalog (Sprint 5에서 확립/검증)

| 패턴 | 적용 | 재사용성 |
|------|------|----------|

### 11.8 Forward-looking Recommendations

1. **VRT(Visual Regression Testing) 도입**: xterm, mermaid 모두 canvas/SVG 기반이라 DOM assertion으로 커버 불가. Playwright screenshot comparison 도입 시 이 두 feature가 첫 번째 대상.

2. **Workspace Awareness → Extension Host 연동**: 현재 webview 내 atom 파생으로 구현했지만, Extension Host가 `workspace.onDidChangeTextDocument` 등 VS Code API를 직접 제공하면 더 정확한 real-time 추적 가능. Delta 없이 postMessage 단건으로 해결 가능한 수준.

3. **Plan Checklist interactive editing**: 현재 read-only 체크리스트. 향후 사용자가 plan item을 reorder/edit/skip 할 수 있는 interactive mode 추가 시, Control Bus를 통한 양방향 통신 필요 (RFC-005 2.1절 Control Bus 활용).

4. **mermaid chunk 최적화**: `mermaid.initialize({ ... })` 시 필요한 diagram type만 등록하는 `lazyLoadedDiagrams` 옵션 활용. 현재 498 kB → 예상 200 kB 수준으로 감소 가능.
