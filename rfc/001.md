# RFC-001: Webview 성능 및 구현 스택

| 항목 | 값 |
|------|-----|
| 상태 | Accepted |
| 작성일 | 2025-03 |
| 선행 | RFC-000 |
| 후속 | RFC-002, RFC-003, RFC-004, RFC-005 |
| SOTA++ | v1 |

---

## 1. 결론

### 1.1 SOTA로 가는 한 줄

React냐 Solid냐가 아니라, **"Webview를 렌더 전용 thin client로 만들고, 이벤트 폭주·대형 payload·메인스레드 연산을 구조로 차단"**하는 게 SOTA임.

### 1.2 최종 제안 요약

| 항목 | 결정 |
|------|------|
| UI | React 19 + TanStack Virtual + Tailwind |
| 상태 | Jotai (atom-per-item 가능 시) 또는 React state + selector |
| 오케스트레이터 | XState v5 (상태 머신 SSOT 강제) |
| 직렬화 | JSON 기본, MessagePack은 Gate 실패 시 옵션. SOTA 업그레이드: [RFC-016](016.md) DELTA_BATCH_BIN (msgpack + Uint8Array) |
| Monaco | 포커스 뷰(상세 diff/부분 적용) 전용, 기본 리스트 렌더러 아님 |

## 2. SOTA 성능 아키텍처

### 2.1 3-버스 구조

| 버스 | 용도 |
|------|------|
| **Delta Bus** | 고빈도, 소형 델타만 전달 |
| **Blob Bus** | 대형 payload는 ref로 요청/응답 |
| **Control Bus** | 상태 전이, 승인 게이트, 세션 제어 |

### 2.2 절대 금지 규칙

1. 전체 AgentState 스냅샷을 고빈도로 postMessage로 보내는 구조 금지
2. large diff 본문/대형 파일 텍스트를 postMessage로 직접 푸시 금지
3. Webview 메인 스레드에서 diff 계산, 대량 파싱, 하이라이팅 금지

### 2.3 절대 필수 규칙

1. Delta는 배치로만 전달
2. UI commit은 16ms 단위로 상한 고정
3. 리스트는 virtualization 필수
4. 대형 데이터는 lazy-load + 캐시 + eviction 정책 필수

---

## 3. SOTA 스택

### 3.1 UI

- React 19
- TanStack Virtual
- Tailwind + (원하면 shadcn/ui)

### 3.2 상태

- **기본안**: React state + normalized store + selector
- **고급안**: Jotai atom-per-item (스트리밍/부분 업데이트 극대화)

SOTA를 가르는 포인트는 "기술명"이 아니라 **정규화 모델 + per-item 구독** 구조임.

### 3.3 오케스트레이터 (SOTA++ 고정)

- **XState v5** 권장 (상태 전이 디버그/리플레이/시각화)
- 대안: Reducer + 이벤트 소싱 (동일 계약 준수)

### 3.4 직렬화

- **기본**: JSON (델타 배치 + ref 기반으로 payload 작게 유지)
- **옵션**: MessagePack (Gate에서 payload bytes/sec, CPU 상한 못 맞출 때만)

### 3.5 Diff/Editor

- **기본**: lightweight diff renderer (블록 단위, 펼침 시에만 로드)
- **포커스**: Monaco (파일/헝크 상세, 부분 적용 UI에서만)

## 4. 프로토콜 SSOT에 성능 잠금

### 4.1 agent-protocol 필수 항목

1. **DELTA_BATCH만 허용** (전체 스냅샷 금지)
2. **streaming_policy** 강제
3. **BlobRef** 규칙 강제 (payload_ref 대체, [RFC-006](006.md))

**DELTA_BATCH 예시**

```
batch_id, created_at_ms
deltas: Delta[]
stats: bytes, delta_count
```

**streaming_policy 예시**

| 필드 | 설명 |
|------|------|
| ui_commit_throttle_ms | 16 |
| max_deltas_per_batch | 상한 |
| max_bytes_per_batch | 상한 |
| max_batches_per_sec | 상한 |
| overflow_behavior | drop_low_priority \| coalesce \| backpressure |

**BlobRef** (payload_ref 대체. SSOT: [RFC-006](006.md) 6절)

| 필드 | 설명 |
|------|------|
| ref_id | 식별자 |
| kind | diff \| file \| llm_output \| api_response \| log \| artifact \| binary \| other |
| approx_bytes | 대략 크기 |
| eviction_hint | hot \| warm \| cold, ttl_ms, pin |

### 4.2 tool-protocol 필수 항목 ([RFC-000](000.md) workspace.* 확장)

1. `workspace.get_blob(ref_id)` — 대형 데이터 fetch
2. `workspace.put_blob` (optional)
3. cache control 힌트 (etag, version, ttl)

postMessage는 "작은 ref"만 오가고, 큰 데이터는 tool 포트로 당겨오는 구조로 고정. workspace 도구 SSOT: [RFC-006 4절](006.md).

## 5. Webview 렌더링 전략

### 5.1 스트리밍 텍스트 처리 (가장 중요)

입력은 자주 오더라도 **UI commit은 최대 60Hz**로 고정.

| 구성요소 | 역할 |
|----------|------|
| inputBuffer | 델타를 쌓기만 함 |
| frameCommit | rAF 또는 16ms 타이머로 한 번에 반영 |
| coalesce | 같은 messageId에 대한 APPEND_TEXT는 프레임 내에서 합침 |

이 구조로 "초당 1000자" 스트리밍 충분히 버팀.

### 5.2 리스트 통합

- 메시지/타임라인을 각각 렌더하면 스크롤/레이아웃 비용 증가
- **단일 Virtual List로 통합**하여 virtualization 한 번만 적용

### 5.3 diff 2단 표현

1. **summary**: 기본 표시 (파일명, 통계, 일부 프리뷰)
2. **full**: 펼쳤을 때만 blob fetch

### 5.4 DOM 노드 수 상한

"보이는 영역 + overscan"을 합쳐 DOM 노드 수가 항상 일정해야 함. 60fps의 본질.

## 6. Gate로 SOTA 강제

### 6.1 gate-performance (필수)

통과 기준은 SSOT로 고정. 예시:

| 메트릭 | 상한 |
|--------|------|
| UI commit/sec | 60 |
| postMessage rx/sec | 설정값 |
| long task count (50ms 이상) | 0 (또는 허용치) |
| frame over 16ms ratio | 허용치 |
| heap growth steady-state | 안정 |

### 6.2 gate-contract (성능 규칙 포함)

- DELTA_BATCH 외 메시지 타입 금지
- BlobRef 없는 대형 텍스트 금지 (bytes 추정치 기준)
- streaming_policy 위반 시 테스트 실패

### 6.3 gate-fixture-replay

- **입력**: golden event log (AgentEvent[] 직렬화)
- **과정**: replay → 최종 UI state 계산
- **검증**: 기대 UI state와 동일성 비교

## 7. Jotai Atom 설계 규칙 (SSOT)

Jotai 채택 시 아래 규칙을 SSOT로 잠글 것.

| 규칙 | 내용 |
|------|------|
| atom 분해 단위 | 메시지/아이템 단위. 세션 전체가 아닌 개별 엔티티별 atom |
| 구독 범위 | 필요한 atom만 구독. 부모 atom이 크면 파생 atom으로 쪼갬 |
| 스트리밍 시 | APPEND_TEXT 등 증분 업데이트는 해당 message atom만 갱신 |
| 정규화 | entities by id, ids by list. 중첩 최소화 |

---

## 8. Worker 분리 대상

Worker로 분리할 heavy compute (메인 스레드 금지):

| 연산 | 이유 |
|------|------|
| diff 계산 (large file) | CPU 집약 |
| 대량 파싱 (JSON, AST) | 메인 스레드 블로킹 |
| 하이라이팅 (syntax) | 토큰화 비용 |
| 토큰 카운팅 | 반복 연산 |

## 9. 구현 순서

### Phase A: 설계 잠금 (구현 최소)

1. agent-protocol: DELTA_BATCH + streaming_policy + BlobRef
2. tool-protocol: get_blob(ref)
3. schemas/agent-ux/gates/performance.v1.yaml + schemas/agent-ux/gates/contract.v1.yaml (schemas/agent-ux/gates/)

### Phase B: UI 뼈대

1. React + TanStack Virtual 단일 리스트
2. normalized store
3. inputBuffer + 16ms commit + coalesce
4. diff summary + lazy expand (get_blob)

### Phase C: 오케스트레이터/상태 머신

1. XState로 core loop 강제
2. 승인 게이트 UI 연결 (review/apply/run)
3. timeline event log + replay

### Phase D: 고급 (Phase C 완료 후)

1. Jotai atom-per-item로 micro-update 최적화 ([RFC-003](003.md))
2. Worker로 heavy compute 분리
3. MessagePack 옵션 도입 여부는 Gate로 결정

**Phase 순서**: A(설계) -> B(UI) -> C(오케스트레이터) -> D(고급). gate-performance는 Phase C 이후([RFC-004](004.md)).

---

## 10. SOTA++ v1 정의 (재정리)

SOTA++는 "무슨 라이브러리 썼냐"가 아니라 다음 4개를 구조로 못 박는 것:

1. **델타 배치 + commit 상한**
2. **ref 기반 대형 payload 분리**
3. **virtualization + lazy expand**
4. **Gate로 성능을 CI에서 강제**
