# RFC-007: 에러 처리 및 복구 UX

| 항목 | 값 |
|------|-----|
| 상태 | Accepted ([REVIEW](RFC-007-009-REVIEW.md)) |
| 작성일 | 2025-03 |
| 선행 | RFC-000, RFC-001, RFC-005, RFC-006 |
| SOTA++ | v1 |

---

## 1. 목표

### 1.1 사용자 관점

- "뭐가 잘못됐는지, 다음에 뭘 할지"가 즉시 보이게 함

### 1.2 개발자 관점

- "재현 가능, 분류 가능, 원인 추적 가능"을 계약으로 고정함

### 1.3 통합 원칙

- 모델/툴/오케스트레이터/웹뷰 어디서 터져도 동일한 UX로 수렴하게 함

---

## 2. 에러 분류 체계 SSOT

### 2.1 SSOT 파일

| 파일 | 용도 |
|------|------|
| `schemas/agent-ux/errors/error-catalog.v1.yaml` | error_code별 메타데이터, safe_message 템플릿, recovery 매핑 |
| `schemas/agent-ux/errors/error-schema.v1.json` | AgentErrorV1 스키마 |

### 2.2 분류 축

| 축 | 값 | 설명 |
|----|-----|------|
| **Layer** | ui \| orchestrator \| model \| tool \| integration | 에러 발생 계층 |
| **Kind** | user_action \| transient \| bug \| policy \| dependency | 에러 유형 |
| **Severity** | info \| warn \| error \| fatal | 심각도 |
| **Retryable** | true \| false | 재시도 가능 여부 |
| **Recovery** | retry_same \| retry_fallback \| reauth \| reduce_scope \| open_logs \| report_issue | 권장 복구 전략 |

---

## 3. Error Boundary 설계

### 3.1 경계 3개 고정

| Boundary | 범위 |
|----------|------|
| **Webview UI** | 렌더/메시지 처리 |
| **Extension Host** | VSCode API 호출, tool 실행 |
| **Orchestrator** | 상태 머신, reducer/effects |

### 3.2 원칙

- boundary는 **"삼키지 않음"**이 원칙임
- 반드시 표준 `AgentErrorV1`로 변환 후 `AgentEvent.ErrorRaised`로 방출함
- boundary 내에서 사용자 UX는 동일한 **Recovery Panel**로 통일함

---

## 4. 사용자용 에러 메시지 정책

### 4.1 원칙

사용자 메시지는 기술 부채를 숨기는 텍스트가 아니라 **"행동 지침"** 중심으로 표준화함

### 4.2 필드

| 필드 | 설명 |
|------|------|
| title | 짧은 제목 |
| what_happened | 1~2문장 요약 |
| what_you_can_do | 버튼/옵션 리스트 |
| scope_hint | 현재 작업 범위 (예: "src/payment/ 이하만") |
| incident_id | trace_id 기반 식별자 |

### 4.3 숨김 정책

- 스택 트레이스, 내부 provider 에러 원문은 기본 숨김
- "자세히 보기"에서만 노출, redaction 정책 적용

---

## 5. Retry UI 설계

### 5.1 원칙

Retry는 "버튼"이 아니라 **"정책 선택"**임

### 5.2 기본 제공 Retry 옵션

| 옵션 | 설명 |
|------|------|
| Retry same step | 동일 상태/동일 입력으로 재시도 |
| Retry with reduced scope | 컨텍스트 축소(선택 파일만) |
| Retry with fallback model | 모델 폴백 |
| Re-run last tool | 마지막 툴 호출만 재실행 |
| Open diagnostics | 로그/타임라인 열기 |

### 5.3 Retry 동작 원칙

- 오케스트레이터 상태를 되돌릴 때 "Undo event"가 아니라 **"Recovery plan event"**로 처리함
- `RecoveryIntentV1`을 만들고, reducer가 다음 상태를 결정함

## 6. 스택 트레이스 노출 정책

### 6.1 SSOT

`schemas/agent-ux/policy/stacktrace-exposure.v1.yaml`

### 6.2 Default

- 사용자에게는 `incident_id`, `layer`, `error_code`, `safe_message`만 노출
- 스택 트레이스는 opt-in 토글로만 제공

### 6.3 Redaction (토글 켜도 적용)

- 토큰/키/Authorization 헤더
- 홈 디렉터리 절대경로 (옵션)
- provider raw payload (옵션)

### 6.4 운영 모드

| 모드 | 스택 노출 |
|------|-----------|
| dev | 기본 노출 가능 |
| prod | 기본 숨김 고정 |

## 8. Gate

| Gate | 역할 |
|------|------|
| **gate-error-catalog** | 모든 error_code는 카탈로그에 존재해야 함, safe_message 템플릿 존재 강제 |
| **gate-recovery-matrix** | retryable=true인 에러는 최소 1개 recovery strategy를 가져야 함 |
| **gate-redaction** | fixture에 민감 문자열 삽입 후, 노출 결과에서 제거됨을 검증함 |
| **gate-ui-error-render** | Error Panel 렌더 스냅샷 (최소) |

## 10. 다음 작업

### 10.1 SSOT 고정

1. error-schema.v1.json 확장 (AgentErrorV1, RecoveryIntentV1)
2. error-catalog.v1.yaml 초안 작성
3. stacktrace-exposure.v1.yaml 작성

### 10.2 agent-protocol 확장

- Control 타입에 `CONTROL_ERROR` payload에 AgentErrorV1 매핑
- AgentEvent에 `ErrorRaised`, `RecoveryRequested` 추가

### 10.3 tool-protocol Error와의 매핑

- ToolResult.error는 tool-protocol의 Error 타입 (code, message, category, retryable)
- Extension Host boundary에서 ToolResult.error를 AgentErrorV1로 변환 후 AgentEvent.ErrorRaised 방출
- 매핑: code→error_code(catalog 등록), category→layer 유추, message→debug_message(redacted), safe_message는 catalog lookup

---

## 11. 보완 및 참고

### 11.1 기존 error-schema와의 호환

- 기존 `code`, `message`, `category` 필드는 `error_code`, `safe_message`, `layer`로 매핑 규칙 정의
- 마이그레이션 기간 동안 양쪽 필드 병행 지원 가능

### 11.2 Recovery Panel UI 스펙

- Recovery Panel은 Webview UI boundary 내 컴포넌트
- `what_you_can_do` 옵션은 버튼으로 렌더, 클릭 시 `RecoveryIntentV1` 이벤트 방출
