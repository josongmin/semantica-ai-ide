## 1. 현재 설계 검증

### 1.1 SOTA++ 방향 일치

현재 설계는 SOTA++ 방향에 맞음.

| 승리 포인트 | 설명 |
|-------------|------|
| BlobRef 강제 | Host에서 "대형 payload는 무조건 BlobRef로 분리"를 강제한 점이 핵심 |
| CONTROL_* ref pull | CONTROL_* 기반 ref pull, ArtifactPanel/Viewer로 "늦게 로드" UX |
| 3-버스 | Delta Bus / Blob Bus / Control Bus 구조 ([RFC-001](001.md)) |

### 1.2 SOTA급으로 올리기 위한 3개 갭

현재 구현은 "동작" 중심. SOTA급으로 올라가려면 아래 3개를 추가로 잠가야 함.

| # | 갭 | 목표 |
|---|-----|------|
| 1 | postMessage 비용 | binary framing(msgpack)으로 JSON 제거, structured clone 비용 축소 |
| 2 | backpressure/coalesce | "예외 throw"가 아니라 "우선순위 lane + 합치기 규칙"으로 고정 |
| 3 | blob/artifact 저장 | 저장 포맷/인덱스/수명 관리가 MVP 수준 → perf 회귀/누수에 취약 |

### 1.3 전제 정리 (정확성)

**VSCode Webview postMessage의 Transferable**: 브라우저 `window.postMessage`처럼 transfer list를 명시적으로 넘기는 API가 아님. **"transfer list로 0-copy 보장"까지는 단정 못함.**

그래도 다음 이득은 확실:
- JSON stringify/parse 제거
- 객체 트리 structured clone 비용 축소 (대형 nested 객체일수록 체감 큼)
- Binary framing(msgpack) + ArrayBuffer/Uint8Array payload

**목표**: "DELTA_BATCH는 무조건 binary"를 계약+게이트로 잠금. host/webview 모두 동일 codec. ack/seq와 결합해 backpressure를 더 강하게 걸 수 있게 함. backpressure **정책** SSOT는 향후 RFC에서 별도 정의.

## 2. Webview ↔ Host 통신 SOTA 업그레이드

### 2.1 DELTA_BATCH_BIN 메시지 포맷 (SSOT)

**Host → Webview**: `DELTA_BATCH_BIN`만 사용. payload는 Uint8Array(또는 ArrayBuffer)로 전달.

```typescript
type DeltaBatchBinEnvelope = {
  type: "DELTA_BATCH_BIN";
  seq: number;
  session_id: string;
  trace_id: string;
  created_at_ms: number;
  encoding: "msgpack";
  bytes: Uint8Array;  // msgpack encoded: { deltas: Delta[] }
};
```

**Webview → Host**: ack는 기존 CONTROL로 유지. `CONTROL_ACK_BATCH { seq }`.

### 2.2 DeltaBatch 포맷에 lane/priority 필드 추가 (다음 단계)

성능은 "무엇을 드랍/합칠 수 있나" 게임.

| 필드 | 값 | 설명 |
|------|-----|------|
| lane | realtime \| interactive \| background | 우선순위 |
| coalesce_key | 예: message_id | 같은 키는 합침 |
| drop_policy | 예: background는 최신만 유지 | backpressure 시 deterministic 처리 |

### 2.3 스트리밍 delta 규칙 강화

현재 APPEND_TEXT chunk overflow를 artifact로 빼는 fallback은 좋으나, SOTA는 **"overflow 자체가 발생하지 않게"** upstream 잠금.

**SSOT 명시**:
- `max_append_per_tick_chars`
- `max_stream_rate_chars_per_sec`
- `max_batches_per_sec`

초과 시 "APPEND_TEXT drop + progress 유지" 같은 deterministic 규칙.

## 3. Backpressure/Queue SOTA 업그레이드

### 3.1 throw 금지, "큐 정책"으로만 수렴

현재 bridge는 초과 시 throw 가능성 있음. SOTA는 "오류"가 아니라 **"정책에 따른 합치기/드랍"**으로 처리.

### 3.2 Ring buffer로 큐 고정

`Array.shift()`는 데이터가 많아지면 비용 증가. SOTA는 **ring buffer**(고정 배열 + head/tail)로 큐 관리.

### 3.3 coalesce map 추가

같은 `message_id`에 대한 연속 APPEND는 "하나로 합쳐서" 전송.

| 단계 | 동작 |
|------|------|
| push | coalesceKey가 같으면 기존 entry에 append |
| flush | 이미 합쳐진 덩어리만 전송 |

## 4. BlobStore/ArtifactIndex SOTA 업그레이드

### 4.1 blob 저장 포맷 분리

**현황**: .json에 meta+payload를 같이 저장. 대형 payload일수록 JSON stringify/parse 병목.

**SOTA 포맷**:
```
.agentux/blobs/<ref_id>/
├── meta.json
└── payload.bin  (또는 payload.txt)
```

- range read/preview 용이
- load 시 meta만 먼저 읽기 가능

### 4.2 sha256 계산 정책 분리

**현황**: putBlob에서 sha256을 항상 계산 (대형 텍스트면 hot path 비용 큼).

**SOTA**:
- sha256는 옵션(또는 background worker)
- "크기만"으로도 1차 운영 가능
- hash는 de-dupe가 필요할 때만 켜는 capability

### 4.3 ArtifactIndex 영속화 + 세션 스냅샷 연동

**현황**: artifactIndexMemory는 개발용으로 충분하나 SOTA claim에는 취약.

**최소 영속화**:
- `.agentux/index/artifacts.<session_id>.jsonl` (append-only)
- 최신 N개는 메모리에 캐시
- 세션 복구/리플레이 완결에 필수

### 4.4 get_blob에 chunked transfer 추가

대형 diff/log는 full load가 아니라 **chunk 기반**이 SOTA. range(lines/bytes)에 "continuation token" 또는 "next_range hint" 추가.

## 5. UI 렌더링 SOTA 업그레이드

### 5.1 ArtifactViewer kind별 렌더러 분리

**현황**: `<pre>`로만 표시.

**SOTA**:
| kind | 렌더러 |
|------|--------|
| diff | 라인 번호 + 변경 하이라이트 → 필요 시 monaco diff |
| log | tail/grep/level filter (전부 ref pull 기반) |
| api_response | JSON viewer(접기) + search |

### 5.2 무거운 컴포넌트 lazy load

monaco/shiki는 **lazy import + "viewer open"에서만 초기화**. 최초 화면은 항상 lightweight DOM.

### 5.3 Virtualization 강제

artifacts list도 커지면 virtualization 필요. **"리스트는 전부 virtual"**을 기본 규칙.

## 6. 유스케이스 보완

### 6.1 외부 LLM 스트리밍

Host에서 "LLM stream → 내부 Stream IR → coalesce → DeltaBatch" 파이프라인 분리.

**SOTA 체크**:
- stream 이벤트는 "raw token"이 아니라 "UI-friendly delta"로만 내려감
- 긴 응답은 자동 blobify + message에는 ref만 (이미 방향 맞음)

### 6.2 외부 API 연결

응답이 큰 경우가 잦음. `api_response` kind 세분화:
- `api_json`, `api_text`, `api_binary`
- UI: "preview(상위 N라인) + full + download(옵션)" 기본 UX

### 6.3 파일 첨부

CONTROL_PUT_BLOB 이미 있음. SOTA로 가려면:
- chunked upload (대파일)
- **AttachmentRef = BlobRef + 파일 메타** SSOT (파일명, size, mime, source, created_at)

### 6.4 플러그인 도구

**SOTA**: 플러그인이 "tool protocol + capability claim + fixture" 3종 세트 기본.

| 항목 | 내용 |
|------|------|
| manifest | tool 목록 + permissions + rate policy 선언 |
| gate-tools | plugin별 permission matrix까지 자동 검증 |
| scaffold | fixture 1개 자동 생성 (이미 방향 맞음) |

## 7. Gate SOTA 업그레이드

### 7.1 gate-performance 예산(budget) SSOT 분리

**현황**: overlay/스냅샷만 있음.

**SOTA**: 예산을 파일로 고정, fixture replay 후 자동 판정.

| 항목 | 예산 (초안) |
|------|-------------|
| INP p95 | < 200ms |
| long task(>50ms) / 10s | < 3 |
| frame over16ms ratio | < 5% |
| postMessage rx/s | < 60 |
| heap growth (10k messages fixture) | < 50MB |

### 7.2 gate-fixtures에 artifact pull 시나리오 추가

1. 대형 diff blobify 발생
2. ArtifactPanel에서 preview load
3. full load

이 3단계를 golden으로 고정 → ref pull 경로 회귀 불가능.

### 7.3 gate-contract에 binary 강제

**DELTA_BATCH 금지, DELTA_BATCH_BIN만 허용**. allowlist에 DELTA_BATCH_BIN 추가, DELTA_BATCH 제거. binaryBridge.spec.ts로 토큰 검증.

## 8. 파일 세트 및 Gate

### 8.1 새 파일

| 경로 | 용도 |
|------|------|
| src/runtime/codec/msgpack.ts | host/webview 공용 encode/decode |
| src/runtime/delta/deltaChannelHostBin.ts | deltaChannelHost의 binary 버전 (RingBuffer, coalesce) |
| src/ui/bridge/installBinaryDeltaHandler.ts | webview 수신 + decode + apply + ack |
| tests/gates/contract/binaryBridge.spec.ts | gate: DELTA_BATCH_BIN 존재, DELTA_BATCH 금지 |

### 8.1.1 DeltaChannelPolicy (deltaChannelHostBin)

| 필드 | 용도 |
|------|------|
| tick_ms | flush 주기 |
| max_inflight_batches | ack 대기 상한 |
| queue_capacity_batches | ring buffer 용량 |
| max_deltas_per_batch | 배치당 최대 델타 수 |
| coalesce_max_append_chars | APPEND_TEXT coalesce 상한 |
| max_queue_overflow_drop_batches | overflow 시 drop할 배치 수 (0이면 throw) |

### 8.2 의존성

`@msgpack/msgpack` 권장 (ESM/TS 호환 안정적).

### 8.3 Gate: DELTA는 binary만

**schemas/agent-ux/gates/contract.v1.yaml** allowlist:
- `DELTA_BATCH` 금지
- `DELTA_BATCH_BIN`만 허용

```
allow: [DELTA_BATCH_BIN, CONTROL_ACK_BATCH, CONTROL_SESSION_CREATE, CONTROL_SESSION_RESTORE,
        CONTROL_SESSION_EXPORT, CONTROL_ACK, CONTROL_ERROR, CONTROL_APPROVAL_REQUEST,
        CONTROL_APPROVAL_DECISION, CONTROL_PLUGIN_LIST, CONTROL_PLUGIN_ENABLE, CONTROL_PLUGIN_DISABLE]
```

**binaryBridge.spec.ts**: UI/host 코드에 `DELTA_BATCH_BIN` 토큰 존재, `DELTA_BATCH` 토큰 없음 검증.

**decode 실패 시**: webview에서 `CONTROL_ERROR` (code: err_bin_decode) 전송 가능. host는 retryable: false로 처리.

### 8.4 Wiring 변경

- Extension: `createDeltaChannelHost` → `createDeltaChannelHostBin` 교체
- Webview: `installMessageHandler` → `installBinaryDeltaHandler` 교체

## 10. SOTA++ 다음 단계

본 RFC의 기반 구현 위에 추가로 잠글 수 있는 **정책/계약/gate 계층**:

| 본 RFC 기반 | 향후 잠금 (RFC-018 후보) |
|-------------|------------------------|
| ring buffer + coalesce map | seq/ack backpressure **정책** SSOT |
| DeltaBatch lane/priority 필드 | DeltaChannel / BlobChannel **논리 분리** |
| blob meta/payload 분리 | quota / eviction / de-dupe **정책** SSOT |
| ArtifactIndex jsonl | append-only event log **계약** |
| sha256 정책 분리 | background hash + alias de-dupe |
| chunked transfer | ref-enforcement 계약 (patch/diff/terminal inline 금지) |

[RFC-017](017.md)은 Monorepo 아키텍처 및 패키지 경계 잠금을 다룬다. 위 정책/계약 항목은 향후 RFC에서 별도 다룰 예정.

## 11. 프론트엔드 갭 분석 및 우선 구현 순서

본 RFC(Webview/Host/Blob/Queue SOTA 업그레이드)를 적용하기 전에, [RFC-001](001.md)/[RFC-002](002.md)/[RFC-003](003.md)/[RFC-004](004.md)에 맞는 프론트엔드 뼈대가 먼저 필요하다. 현재 구현과 RFC-001 스펙 간 갭을 정리한다.

### 11.1 RFC-001 vs 현재 구현 갭

| 항목 | RFC-001 | 현재 구현 |
|------|---------|-----------|
| 메시지 리스트 | VirtualMessageList + MessageRow | 없음. App에 DevOverlay/ReplayPanel만 있음 |
| 스트리밍 엔진 | inputBuffer + 16ms commit + coalesce | 없음 |
| 상태 관리 | store 또는 jotaiStore | 없음 |
| perfCollector | window.__perf 제공 | 없음. DevOverlay가 표시할 데이터 없음 |
| testHarness | window.__agentUx 제공 | 없음. ReplayPanel이 "missing window.agentUx" 표시 |

### 11.2 의존성 차이

| RFC-001 | 현재 package.json |
|---------|-------------------|
| React 19 | React 18 |
| TanStack Virtual | 없음 |
| Jotai | 없음 |
| Tailwind | 없음 |

### 11.3 구조 차이

- **RFC-010 FSD**: app/pages/widgets/features/entities/shared 구조 없음
- **Delta 타입**: types.ts 없음 → DELTA_BATCH 처리 불가

### 11.4 우선 구현 순서 제안

1. **types.ts** – Delta, UiMessage, DeltaBatch 타입 정의
2. **perfCollector.ts** – window.__perf 주입 (DevOverlay 동작)
3. **testHarness.ts** – window.__agentUx 주입 (ReplayPanel 동작)
4. **store.ts** 또는 **jotaiStore.ts** – 메시지 상태 관리
5. **streaming.ts** – inputBuffer + 16ms commit + coalesce
6. **MessageRow.tsx** – 개별 메시지 렌더
7. **VirtualMessageList.tsx** – TanStack Virtual 기반 리스트
8. **App.tsx** – VirtualMessageList + DevOverlay + ReplayPanel 통합

이 순서로 구현하면 RFC-002/003/004에 맞는 프론트엔드 뼈대를 맞출 수 있다.
