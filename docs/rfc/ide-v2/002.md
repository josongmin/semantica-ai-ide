1. Summary

Query Gateway는 Frontend가 Semantica 엔진의 고급 분석 기능을 호출하는 유일한 진입점이다.

역할:

여러 엔진 query를 의도 기반 API로 묶는다

엔진 응답을 UI ViewModel 계약으로 변환한다

긴 실행 작업을 Job 기반으로 관리한다

Query fan-out / caching / batching을 수행한다

Frontend는 아래만 호출한다.

Integration Kernel
├ LSP Session Manager
├ Query Gateway ← 분석 기능
├ Event Bridge
└ Policy Translator 2. 문제 정의

Semantica 엔진은 다음 특징을 가진다.

특징 설명
Query 종류 많음 Q0~Q5 + 30+
결과 구조 복잡 분석 중심 데이터
다중 Query 필요 하나의 UX에 여러 query 필요
실행 시간 다양 ms ~ 수십초

Frontend가 직접 Query를 호출하면 문제가 발생한다.

문제 설명
coupling 증가 UI가 engine query 타입에 의존
state explosion job 상태 관리 어려움
fan-out 처리 불가 UI에서 여러 query orchestration 필요
변경 취약 query 추가 시 UI 수정 필요

따라서 Query Gateway를 통해 의도 기반 API로 노출해야 한다.

3. 설계 목표
   3-1. Intent-Based API

Query는 엔진 기준이 아니라 사용자 의도 기준으로 제공된다.

예:

엔진 기준

pta_query
dfg_query
taint_query
clone_query

UI 기준

impact analysis
review evidence
slice graph
findings dashboard
3-2. Query Aggregation

하나의 UI 기능은 여러 query 조합으로 구성된다.

예:

Review Evidence

impact_analysis

- taint_findings
- clone_detection
- complexity_metrics
- test_impact

Query Gateway가 이를 수행한다.

3-3. Long-Running Job 지원

분석 시간이 긴 작업은 Job으로 실행한다.

예:

Query 예상 시간
impact 200ms
slicing 500ms
taint analysis 5s
clone detection 10s

Job은 Event Bridge와 연결된다.

6-1. Gateway Interface
interface QueryGateway {

getImpact(input: ImpactQueryInput): Promise<ImpactGraphViewModel>

getSlice(input: SliceQueryInput): Promise<SliceViewModel>

getFindingsDashboard(input: FindingsInput): Promise<FindingsDashboardViewModel>

getReviewEvidence(input: ReviewEvidenceInput): Promise<ReviewEvidenceViewModel>

getReplayTimeline(input: ReplayTimelineInput): Promise<ReplayTimelineViewModel>

}
6-2. Job API
interface QueryJob {

id: string
status: "running" | "completed" | "failed"

progress?: number

result?: unknown
}
6-3. Job Manager
interface QueryJobManager {

start(query: QueryIntent): Promise<QueryJob>

cancel(jobId: string): Promise<void>

get(jobId: string): Promise<QueryJob>
} 7. ViewModel Contracts

상황 정책

Gateway는 다음을 검증한다.

항목 이유
workspace scope 다른 repo 접근 방지
query limit 과부하 방지
capability check 위험 작업 제한 12. Acceptance Criteria

구조 기준:

Frontend는 engine query를 직접 호출하지 않는다

모든 고급 분석은 Query Gateway를 통한다

Job 기반 실행이 가능하다

기능 기준:

impact/slice/findings/review query 제공

결과는 ViewModel 형태로 반환

확장 기준:

새 query 추가 시 UI 변경 최소화

13. 핵심 결론

Query Gateway는 Semantica IDE에서 LSP 다음으로 중요한 계층이다.

이 계층이 없으면:

Frontend
↔ Engine
coupling 폭발

Gateway를 두면:

Frontend
↔ Query Gateway
↔ Engine

구조 안정성이 유지된다.
