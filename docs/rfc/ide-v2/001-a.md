2-1. 현재 상태

Semantica CodeGraph V2는 이미 아래를 제공함.

7개 언어 지원

Q4 IDE 기능 20개 실구현

Q0~Q5 query surface

REST API, MCP, CLI, Playground

Proof/Evidence/Replay 기반

Program slicing, taint, PTA, clone, MemSSA 등 고급 분석

즉 현재 제품 병목은 엔진 기능 부족이 아님.

2-2. 진짜 병목

현재부터의 병목은 아래임.

프론트가 엔진 기능을 어떻게 안정적으로 소비할 것인가

LSP 기능과 비-LSP 고급 분석 기능을 어떻게 분리할 것인가

Agent/Review/Replay/Impact/Slice 결과를 어떤 상태모델로 UI에 투영할 것인가

기능이 계속 늘어나도 UI 구조가 흔들리지 않게 할 수 있는가

2-3. 핵심 리스크

프론트가 엔진과 직접 결합되면 아래 문제가 생김.

query 타입 변경 시 UI 전체 흔들림

엔진 결과 포맷이 곧 UI 상태가 되어 결합도 폭증

LSP와 고급 분석 기능이 섞여 경계 붕괴

증분 분석, 타임라인, replay, review가 각자 다른 계약으로 분기

플러그인 추가 시 shell 무너짐

따라서 Frontend와 Engine 사이에 Integration Kernel이 반드시 필요함.

6. Integration Kernel 상세
   6-1. LSP Session Manager
   역할

Q4 query layer를 editor가 기대하는 LSP semantics로 노출함.

책임

document open / change / close 관리

language별 session lifecycle

incremental sync

cancellation token 전파

LSP request/response correlation

diagnostic publish 브로드캐스트

제공 기능

textDocument/\*

workspace/\*

hierarchy

semantic tokens

diagnostics stream

규칙

editor-specific adapter는 LSP Session Manager 위에만 존재

Monaco/Zed/CodeMirror는 LSP 추상 인터페이스만 소비

frontend는 Q4 query 파일 경로/구현체를 직접 알지 않음

6-2. Query Gateway
역할

LSP 밖의 Semantica 고급 기능을 UI 친화적 질의면으로 제공함.

대상 기능

impact analysis

slicing

explain query

findings dashboard

clone detection

taint findings

service graph

architecture validation

proof bundle fetch

review evidence fetch

replay compare fetch

설계 원칙

query는 의도 단위로 노출

엔진 내부 query 개수나 레이어를 프론트에 드러내지 않음

Query Gateway가 내부적으로 여러 query를 fan-out 가능

예:

getReviewBundle(changeSetId)
-> impact_analysis
-> taint_findings
-> clone_detection
-> design_metrics
-> test evidence
-> proof assembly
6-3. Result Normalizer
역할

엔진 응답을 UI 전용 canonical model로 바꿈.

이유

엔진 응답은 아래 특징을 가짐.

분석 중심 구조

query별 shape 상이

세부 필드가 너무 많음

UI에서 바로 쓰기엔 과도하게 low-level임

예시 변환
Engine Result
-> ImpactAnalysisRaw
-> TaintRaw
-> CloneRaw
-> MetricsRaw

Result Normalizer
-> ReviewEvidenceCard[]
-> ImpactNode[]
-> SecurityDeltaSummary
-> ComplexityDeltaSummary
원칙

UI는 raw engine result를 직접 저장하지 않음

정규화 모델은 stable contract로 관리

view별 projection은 normalizer 이후에만 허용

6-4. Event Bridge
역할

엔진/agent/runtime 이벤트를 UI 이벤트 모델로 변환하고 append-only state로 투영함.

입력 이벤트 예시

indexing_started

indexing_progress

indexing_completed

analysis_started

analysis_completed

agent_step_started

agent_step_completed

approval_requested

approval_resolved

review_generated

checkpoint_created

timeline_appended

출력 이벤트 예시

ui.analysisJob.updated

ui.agentRun.updated

ui.review.ready

ui.timeline.appended

ui.approval.pending

규칙

Event Bridge는 append-only log와 정렬되어야 함

replay 가능한 이벤트만 canonical state에 반영

ephemeral UI effect는 별도 레이어로 분리

6-5. Capability / Policy Translator
역할

엔진/agent/runtime의 capability와 policy verdict를 UI 승인 흐름으로 변환함.

예시
Backend Capability UI Policy Surface
filesystem.write auto / warn / approval
git.commit approval required
network.call approval required
destructive edit human review
high-risk patch proof review required
원칙

policy 판단은 backend source of truth를 존중

UI는 policy를 임의 재해석하지 않음

단, 사용자 표시용 explanation은 번역해서 제공

10-1. state layer 매핑

Integration Kernel은 기존 5-layer state architecture와 정렬되어야 함.

State Layer Kernel 연결 방식
S1 Persistent Layout 직접 연결 없음
S2 Session Workspace LSP session, active repo, indexing state
S3 View Local normalized result projection만 저장
S4 Domain State review, timeline, approvals, findings
S5 Ephemeral hover, temporary loading, transient toast
10-2. 원칙

Kernel snapshot은 S2/S4 중심

View filtering/sorting은 S3

UI animation/loading은 S5

raw transport payload는 상태 저장 금지

12. Acceptance Criteria
    12-1. 구조 기준

Frontend는 raw engine query를 직접 호출하지 않음

LSP와 non-LSP 분석 호출 경계가 분리됨

이벤트 기반 상태는 Event Bridge 한 곳으로 수렴

UI는 normalized contract만 소비

12-2. 제품 기준

baseline editor 기능 14종 이상 정상 작동

impact/slice/review evidence 패널이 별도 surface로 노출

indexing/agent/review/timeline 상태가 append-only event로 재구성 가능

capability/risk verdict가 승인 UX에 반영됨

12-3. 확장 기준

Monaco 외 editor adapter 추가 가능

backend transport가 REST/IPC/LSP 혼합이어도 UI contract 유지

plugin contribution이 kernel contract 위에서 동작 가능

13. 기대 효과
    13-1. 기술 효과

프론트-엔진 결합도 절감

query 변화에 대한 UI 안정성 확보

replay/review/analysis/event 일관성 확보

editor baseline과 Semantica differentiation 경계 명확화

13-2. 제품 효과

그냥 강한 LSP가 아니라 analysis-native IDE가 됨

slicing/impact/evidence/replay가 chat 보조 기능이 아니라 1급 surface가 됨

이후 multi-agent / proof-carrying patch / speculative execution까지 자연 확장 가능
