1. Summary

이 문서는 Semantica DevOS 플랫폼의 최상위 규칙 문서(Constitution)다.

모든 RFC는 이 문서에 정의된 원칙과 구조를 따라야 한다.

2. 플랫폼 정체성

Semantica DevOS는 Feature-first IDE가 아니라 Capability-first DevOS Platform이다.

목표 구조:

Surface 추가 가능
Client 추가 가능
Repo 추가 가능
Agent 추가 가능
Runtime 추가 가능
Graph 추가 가능
정책 추가 가능
하지만
Core contract는 안 흔들리게

3. 고정 축 (8개)

앞으로 어떤 기능이 와도 안 흔들려야 하는 최소 골격:

축 고정할 것

Runtime local / remote / distributed execution contract

State cross-surface state contract

4. 설계 원칙

4.1 Surface와 Runtime 분리

UI가 강해도 runtime 안 건드림.
runtime이 분산돼도 UI 안 건드림.

4.2 Query와 Event 분리

읽기 = query.
상태변화 = event.

4.3 Multi-repo 기준 설계

처음부터 workspace에 repo N개 기준으로 설계한다.

4.4 Multi-agent 기준 설계

처음부터 agent fleet 기준으로 설계한다.

4.5 모든 기능은 capability로 붙음

기능을 화면 단위로 설계하면 나중에 지저분해짐.
반드시 capability 단위로 쪼개야 함.

6. Surface 목록 (SSOT)

DevOS의 UI Surface는 정확히 6개다.

Surface RFC 역할
Editor RFC-002 코드 편집 + inline analysis
Review Evidence RFC-004 patch evidence review
Temporal Replay RFC-005 timeline / replay / checkpoint
Agent Workspace RFC-006 agent 작업 환경
Repository Knowledge Graph RFC-007 코드베이스 그래프 탐색
Multi-Agent Orchestrator RFC-008 multi-agent 운영

다음은 Surface가 아니라 Core Infrastructure다:

계층 RFC 역할
Integration Kernel RFC-001 frontend ↔ engine 통합
Query Gateway RFC-003 분석 query orchestration
Event Bridge RFC-001/010 이벤트 스트리밍 + state projection
Policy Translator RFC-001 capability / approval 변환

주의: 기존 RFC-001에서 언급된 Runtime Surface는 RFC-014(Runtime Abstraction)에 흡수됨.
Runtime은 독립 UI Surface가 아니라 Platform Kernel의 일부로 관리된다.

8. 절대 규칙

Rule 1 — Frontend는 engine raw type 직접 소비 금지
Engine → Query Gateway → Result Normalizer → ViewModel → Surface

Rule 2 — Surface는 서로 직접 상태 수정 금지
Surface action → Event → Projection → State → Other Surface update

Rule 3 — Runtime location을 UI가 알면 안 됨
UI는 task running / progress / result만 알면 됨.

Rule 4 — Repo를 경로 기반으로만 다루지 말 것
항상 workspaceId + repoId 기준.

Rule 5 — 모든 mutation은 event로 표현
Domain state 직접 변경 금지.

Rule 6 — 새 기능 추가 흐름
새 기능 → capability 등록 → query 추가 → event 추가 → projection 추가 → surface 연결

10. 핵심 결론

이 Constitution은 DevOS의 모든 설계 결정의 기준점이다.

새 RFC를 작성할 때는 반드시 이 문서의 원칙, 계층 구조, canonical 모델, 절대 규칙을 따라야 한다.

이 문서가 변경되면 하위 RFC에 영향이 전파되므로 변경 시 전체 RFC 정합성을 검증해야 한다.
