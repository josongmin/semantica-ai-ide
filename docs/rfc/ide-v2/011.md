1. Summary

Proof-Carrying Patch Flow는 agent가 생성한 patch에 정적 분석 증거를 부착하는 시스템이다.

기존 AI coding:
patch → human review → merge

Semantica:
patch + proof bundle → automated verdict → human review → merge

patch가 "왜 안전한지"를 스스로 증명하는 구조다.

2. Problem Statement

현재 AI agent가 생성하는 patch의 문제:

문제 설명
impact 불명 patch가 어디에 영향을 미치는지 모름
security 불명 새로운 취약점이 생기는지 모름
complexity 불명 코드 품질이 나빠지는지 모름
test coverage 불명 어떤 테스트가 영향받는지 모름
clone 불명 중복 코드가 생기는지 모름

Semantica 엔진은 이미 이 분석을 수행할 수 있다. 부족한 것은 patch와 evidence를 연결하는 구조화된 흐름이다.

3. Goals

3.1 Proof Bundle — patch에 부착되는 증거 묶음 정의
3.2 Automated Verdict — proof bundle 기반 자동 판정 생성
3.3 Review Integration — verdict를 Review Evidence Surface에 연결
3.4 Policy Gate — verdict 결과에 따라 자동 승인/거부/수동 리뷰 분기

4. Architecture

Agent generates patch
↓
Proof Builder (Engine)
├ impact_analysis
├ taint_analysis
├ clone_detection
├ complexity_metrics
└ test_impact
↓
Proof Bundle

5. Proof Bundle Model (canonical)

interface ProofBundle {
  id: string
  patchId: string
  timestamp: number
  impact: ImpactProof
  security: SecurityProof
  clone: CloneProof
  metrics: MetricsProof
  tests: TestProof
}

interface ImpactProof {
  affectedFiles: number
  affectedFunctions: number
  affectedModules: string[]
  callChainDepth: number
}

interface SecurityProof {
  newVulnerabilities: number
  fixedVulnerabilities: number
  taintPaths: TaintPath[]
  verdict: "clean" | "warning" | "critical"
}

interface CloneProof {
  newClones: number
  removedClones: number
  cloneGroups: CloneGroup[]
}

interface MetricsProof {
  complexityDelta: number
  maintainabilityDelta: number
  cognitiveComplexityDelta: number
}

interface TestProof {
  affectedTests: number
  passingTests: number
  failingTests: number
  coverageDelta: number
}

6. Verdict Model

interface PatchVerdict {
  id: string
  proofBundleId: string
  patchId: string
  outcome: "safe" | "warning" | "unsafe" | "unknown"
  confidence: number
  reasons: VerdictReason[]
  recommendation: "auto_approve" | "human_review" | "auto_reject"
}

interface VerdictReason {
  category: "impact" | "security" | "clone" | "metrics" | "tests"
  level: "pass" | "warning" | "fail"
  message: string
}

7. Verdict Rules

7.1 Auto-approve 조건
security.verdict === "clean"
AND impact.affectedFiles <= threshold
AND tests.failingTests === 0
AND metrics.complexityDelta <= threshold
AND clone.newClones === 0

7.2 Auto-reject 조건
security.verdict === "critical"
OR tests.failingTests > 0 AND coverageDelta < 0

7.3 Human-review (기본)
위 두 조건에 해당하지 않는 모든 patch

8. Policy Gate Integration

Verdict는 Capability/Policy Translator(RFC-001)와 연결된다.

Verdict 결과 Policy Action
auto_approve patch 자동 적용
human_review Review Surface에 evidence 표시, 사용자 승인 대기
auto_reject patch 거부, 이유 표시

Policy는 workspace/org 단위로 threshold를 설정할 수 있다.

9. Review Surface 연동

Review Evidence Surface
├ Diff Viewer — patch 내용
├ Proof Cards — proof bundle 시각화
│   ├ Impact Card
│   ├ Security Card
│   ├ Clone Card
│   ├ Metrics Card
│   └ Test Card
├ Verdict Badge — safe / warning / unsafe
└ Review Controls — approve / reject / request changes

10. Event Integration

이벤트는 RFC-002-V2의 workspace-aware DevOSEvent를 사용한다 (RFC-012 섹션 7 참조).

Event 설명
proof_build_started proof 수집 시작
proof_build_completed proof bundle 완성
verdict_generated 판정 완료
verdict_overridden 사용자가 판정 재정의
patch_approved patch 승인
patch_rejected patch 거부

11. Agent Workflow Integration

Multi-Agent Orchestrator(RFC-008)와의 연결:

Agent generates patch
↓
Orchestrator triggers proof build
↓
Proof Bundle assembled
↓
Verdict generated
↓
If multi-candidate: Convergence Pane에서 verdict 비교
If single-candidate: Policy Gate에서 분기

12. Temporal Integration

모든 proof/verdict는 Temporal Store(RFC-005)에 append된다.

이를 통해:
- 과거 patch의 proof를 재조회 가능
- verdict 변경 이력 추적 가능
- patch lineage 위에 proof lineage 구성 가능

13. Performance Strategy

기술 설명
parallel proof 각 proof dimension 병렬 수집
incremental proof 변경된 파일만 분석
proof cache 동일 changeset 재분석 방지

14. Acceptance Criteria

구조:
- proof bundle은 Query Gateway를 통해 조회
- verdict는 Policy Translator와 연결
- event는 Event Bridge를 통해 전파

기능:
- patch에 proof bundle 부착 가능
- verdict 자동 생성 가능
- Review Surface에서 proof 시각화 가능

확장:
- 새 proof dimension 추가 가능 (e.g., license, architecture rule)
- verdict rule을 workspace 단위로 커스터마이징 가능

15. 핵심 결론

Proof-Carrying Patch Flow는 Semantica를 다음 단계로 끌어올린다.

AI IDE → DevOS → Autonomous Verified Development System

agent가 생성한 patch는 "그럴듯한 코드"가 아니라 "증거가 부착된 검증 가능한 변경"이 된다.
