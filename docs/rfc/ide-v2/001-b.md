1. 한줄 결론

지금부터는 기능 목록을 더 추가하는 것보다, 앞으로 나올 기깔난 확장기능들을 아키텍처 변경 없이 꽂을 수 있는 플랫폼 구조를 먼저 잠가야 함.

핵심은 이것임.

Surface 추가 가능
Client 추가 가능
Repo 추가 가능
Agent 추가 가능
Runtime 추가 가능
Graph 추가 가능
정책 추가 가능
하지만
Core contract는 안 흔들리게

즉 목표 구조는 Feature-first IDE가 아니라 Capability-first DevOS Platform 이어야 함.

2. 최상위 설계 원칙
   2-1. 먼저 잠가야 할 것

앞으로 어떤 기능이 와도 안 흔들려야 하는 최소 골격은 아래 8개임.

축 반드시 고정할 것
Client Desktop / Web / Mobile 공통 client contract
Surface UI surface contract
Workspace repo / user / agent / session identity
Runtime local / remote / distributed execution contract
Query analysis / graph / review / replay query contract
Event append-only event contract
State cross-surface state contract
Policy capability / approval / risk contract

이 8개가 고정되면 나중 확장은 대부분 새 기능 추가로 끝나고 구조 재작성이 필요 없어짐.

2-2. 설계 원칙 5개

1. Surface와 Runtime 분리
   UI가 강해도 runtime 안 건드림
   runtime가 분산돼도 UI 안 건드림
2. Query와 Event 분리
   읽기 = query
   상태변화 = event
3. Single-repo를 기준으로 설계하지 않음

처음부터

repo 1개
아님
workspace에 repo N개

기준으로 설계해야 함.

4. Single-agent를 기준으로 설계하지 않음

처음부터

agent 1개
아님
agent fleet

기준으로 설계해야 함.

5. 모든 기능은 capability로 붙음

기능을 화면 단위로 설계하면 나중에 지저분해짐.
반드시 capability 단위로 쪼개야 함.

예

impact_analysis
proof_review
context_pack
timeline_replay
service_graph
remote_execution

4-1. Platform Kernel

이게 제일 중요함.
지금까지 만든 RFC들 중 사실상 제일 먼저 더 강하게 잠가야 하는 것도 이 부분임.

Kernel 책임은 아래 6개만 가져가면 됨.

Kernel 책임 설명
Identity workspace / repo / user / agent / session 식별
Routing 어떤 query/event/runtime로 보낼지 결정
Projection backend state를 UI state로 변환
Capability 기능 권한/정책 판단
Transport abstraction IPC/HTTP/WebSocket/stdin 차이 흡수
Federation multi-repo / multi-runtime 묶기

즉 앞으로 어떤 기능이 들어와도 결국

새 기능
→ capability 등록
→ query 추가
→ event 추가
→ projection 추가
→ surface 연결

이 흐름으로 끝나야 함.

4-2. Workspace Identity & Federation Layer

이건 진짜 미리 넣어야 함.
안 넣으면 나중에 multi-repo, mobile, collaboration, distributed agent 다 꼬임.

최소 identity 모델은 이것이면 충분함.

interface WorkspaceId {
workspaceId: string
}

interface RepositoryId {
workspaceId: string
repoId: string
}

interface SessionId {
workspaceId: string
userId: string
sessionId: string
}

interface AgentId {
workspaceId: string
sessionId: string
agentId: string
}

interface RuntimeId {
workspaceId: string
runtimeId: string
kind: "local" | "remote" | "worker"
}

핵심은 모든 객체가 workspace 기준으로 귀속되어야 한다는 점임.

4-3. Query Gateway를 workspace-aware로 만들기

지금 Query Gateway가 좋아도 single-repo 전제로 짜면 나중에 다시 엎어야 함.

처음부터 입력을 이렇게 잡는 게 맞음.

interface QueryContext {
workspaceId: string
repoIds?: string[]
runtimeId?: string
sessionId?: string
agentId?: string
}

모든 query는 이 context를 포함해야 함.

예

getImpact({
context: { workspaceId, repoIds: ["frontend", "backend"] },
target: ...
})

이렇게 해두면 나중에 multi-repo impact, cross-repo references, service flow tracing이 자연스럽게 됨.

4-4. Event Model을 전역 append-only로 잠금

나중 확장을 제일 잘 받는 구조는 결국 event 구조임.

이벤트 최소 공통 필드는 아래면 충분함.

interface DevOSEvent {
id: string
timestamp: number
workspaceId: string
sessionId?: string
repoId?: string
agentId?: string
runtimeId?: string

domain:
| "editor"
| "analysis"
| "agent"
| "review"
| "timeline"
| "graph"
| "workspace"
| "policy"

type: string
payload: unknown
}

이걸 해두면

replay

collaboration

mobile mirror

distributed runtime monitoring

audit

approval flow

cross-surface sync

전부 같은 기반으로 해결 가능함.

5. 앞으로 예상되는 기깔난 확장기능과 어떻게 꽂히는지
   5-1. 동시편집

즉 Kernel/Query/Event 계약만 살아 있으면 붙이기 쉬움.

5-2. 모바일 개발

추가되는 것

Remote Control Surface

붙는 위치

Mobile Client
→ Platform Kernel
→ same Query/Event/Policy

즉 모바일은 runtime 새로 만드는 게 아니라 client 추가임.

5-3. Multi-Repo Workspace

추가되는 것

Repo Federation Layer
Workspace Graph

붙는 위치

Workspace Identity
→ Query Context
→ Knowledge Platform

즉 single-repo graph를 workspace graph로 승격하면 됨.

5-4. Microservice Map

추가되는 것

Service Graph Builder
Infra Graph Builder
Runtime Edge Collector

붙는 위치

Knowledge Platform
→ Repo Graph 확장
→ Surface는 그대로 재사용

즉 graph type 하나 더 추가하는 구조로 가야 함.

5-5. 여러 프로젝트 맥락 이해

Cross-Repo Slice

붙는 위치

Query Gateway
→ Context Pack Builder
→ Agent Workspace / Orchestrator

즉 Query Gateway가 multi-repo aware면 바로 가능해짐.

5-6. Distributed Agent / Worker Pool

추가되는 것

Worker Scheduler

붙는 위치

Execution Platform

UI는 Event와 Query만 보면 되므로 거의 안 바뀜.

5-7. Autonomous Development Loop

추가되는 것

Planner
Verifier

붙는 위치

Orchestrator Surface
Policy Engine
Proof Store

즉 이미 만든 surface 위에서 확장 가능함.

6. 최소 확장성을 유지하려면 절대 깨면 안 되는 규칙
   6-1. Frontend가 engine raw type 직접 소비 금지

무조건

Engine
→ Query Gateway
→ Result Normalizer
→ ViewModel
→ Surface

이 흐름만 허용해야 함.

6-2. Surface가 서로 직접 상태 수정 금지

무조건

Surface action
→ Event
→ Projection
→ State
→ Other Surface update

로 가야 함.

6-3. runtime location을 UI가 알면 안 됨

UI는 아래만 알면 됨.

task running
job running
progress
result

local인지 remote인지 worker pool인지 모르게 해야 나중 확장이 쉬움.

6-4. repo를 경로 기반으로만 다루지 말 것

항상

workspaceId + repoId

기준으로 다뤄야 함.

6-5. 그래프는 단일 graph가 아니라 layered graph여야 함

최소한 아래는 분리해야 함.

Graph Layer 의미
Symbol Graph 함수/클래스/심볼
Dependency Graph 모듈/패키지
Service Graph 서비스 간 관계
Workspace Graph repo 간 관계
Org Graph 조직 전체 지식 그래프

처음부터 layered graph로 잡아야 확장성이 좋음.

7. 실제로 먼저 만들어야 하는 최소 SSOT 문서 세트

기능 문서보다 먼저, 아래 6개 문서가 제일 중요함.

7-1. Platform Constitution

플랫폼 전체의 최상위 규칙 문서

7-2. Workspace Identity & Federation Contract

multi-user / multi-repo / multi-agent / multi-runtime 잠금

7-3. Query & Event Canonical Schema

query와 event 공통 구조 잠금

7-4. Runtime Abstraction Contract

local / remote / worker pool / mobile server mode 흡수

7-5. Knowledge Graph Layering Contract

symbol/service/workspace/org graph 구조 잠금

7-6. Capability & Policy Contract

승인/위험/권한/자동화 정책 잠금

즉 먼저 기능이 아니라 플랫폼 계약을 잠그는 게 맞음.

8. 추천하는 최종 아키텍처 방향
   8-1. 가장 좋은 방향
   Semantica DevOS
   = Surface Platform

- Query/Event Platform
- Workspace Federation Platform
- Distributed Runtime Platform
- Knowledge Graph Platform

즉 IDE가 아니라 개발 운영 플랫폼으로 잡아야 함.

8-2. 나쁜 방향
Monaco 중심으로 먼저 만들고
필요할 때마다 기능 붙이기

이렇게 가면

collaboration 때 다시 뜯어고침

하게 됨.

8-3. 좋은 방향
Platform contract 먼저

확장은 capability와 adapter로

이게 SOTA 방향임.

9. 최종 추천

지금 질문에 대한 가장 정확한 답은 이것임.

먼저 만들어야 하는 것은 기능 아키텍처가 아니라 플랫폼 아키텍처임.

그 플랫폼은 최소한 아래를 만족해야 함.

multi-client 가능

multi-repo 가능

multi-agent 가능

distributed runtime 가능

layered graph 가능

event-sourced projection 가능

capability/policy 중심 확장 가능

이 구조만 먼저 잠그면, 나중에 떠오르는 기깔난 기능들은 대부분

새 capability 추가
새 query 추가
새 event 추가
새 surface 추가
새 adapter 추가

수준으로 끝남.
